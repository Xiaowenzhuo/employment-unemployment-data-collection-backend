## 2. 第一周五张基础表（服务器已通过 V1 建立）

下表保留第一周纲领明确写出的字段类型与约束；服务器实际结构以已执行的 `V1__core_schema.sql` 为准。

| 表 | 字段（设计类型） | 已明确的键与约束 | 用途 |
|---|---|---|---|
| `region` | `code VARCHAR(12)`；`parent_code VARCHAR(12)`；`name VARCHAR(80)`；`level TINYINT` | `code` 主键；`parent_code` 建索引 | 省、市、县地区树；供组织归属和地区列表查询使用。 |
| `org_unit` | `id BIGINT`；`parent_id BIGINT`；`org_type VARCHAR(20)`；`region_code VARCHAR(12)`；`name VARCHAR(120)`；`enabled BOOLEAN` | `id` 主键；`parent_id` 引用本表上级组织；`org_type` 暂用 `PROVINCE`、`CITY`、`ENTERPRISE` | 省、市、企业组织及固定的所属地区。 |
| `user_account` | `id BIGINT`；`org_id BIGINT`；`username VARCHAR(64)`；`password_hash VARCHAR(100)`；`display_name VARCHAR(80)`；`enabled BOOLEAN`；`created_at DATETIME(3)` | `id` 主键；`username` 唯一；`org_id` 引用 `org_unit.id` | 登录身份。只存 BCrypt 密码哈希，不存明文；时间按 UTC 保存。 |
| `role` | `id BIGINT`；`code VARCHAR(32)`；`name VARCHAR(50)` | `id` 主键；`code` 唯一；基础角色代码为 `ENTERPRISE`、`CITY`、`PROVINCE` | 登录后的角色标识与权限分流。 |
| `user_role` | `user_id BIGINT`；`role_id BIGINT` | (`user_id`, `role_id`) 联合主键；两列分别引用 `user_account.id`、`role.id` | 用户与角色的关联。第一周每个演示用户只分配一种角色，但保留关联表。 |

关系简图：`region` → `org_unit` → `user_account` → `user_role` ← `role`；`org_unit.parent_id` 和 `region.parent_code` 分别表示各自的层级。现有 `V1` 已给 `org_unit.region_code` 设置外键和索引，给 `region.parent_code` 设置父级外键；未配置级联删除，删除受引用记录时由外键阻止。

企业名称、组织机构代码、联系人等**企业业务资料不放进 `user_account`**。老师需求的流程是省级创建企业账号，企业登录后补全资料并提交备案；业务资料和备案相关表在后续迭代设计。

| 新表 | 关键字段与约束 | 用途 |
|---|---|---|
| `id_allocator` | `entity_name VARCHAR(30)` 主键；`next_id BIGINT NOT NULL` | 按组织、用户、备案单分别分配 ID。迁移时根据现有最大 ID 初始化组织/用户下一号，且最低从 1000 起；建号事务通过 `SELECT ... FOR UPDATE` 锁行取号，不在每次请求中扫描 `MAX(id)`。 |
| `filing_option` | `code VARCHAR(64)` 主键；`category`、`parent_code`、`name`、`demo`；父代码外键；类别/父代码索引 | 企业性质、所属行业、联系地址的两级选项。V3 插入仅供联调的 `DEMO_` 演示选项，不能视为正式云南编码。 |

| `enterprise_filing` | `id BIGINT` 主键；`org_id BIGINT` 唯一且引用企业组织；`status`、`current_version`、14 项可编辑资料、`updated_at`；`organization_code VARCHAR(9)` 唯一且可空；状态索引 | 每家企业一条稳定备案单，保存当前草稿和状态。草稿可缺字段，完整校验后才能提交。所属地区继续取 `org_unit.region_code`，企业不能改。 |
| `filing_version` | (`filing_id`, `version`) 联合主键；14 项提交快照；`result`、`submitted_at/by`、`reviewed_at/by`、`reason`；关联备案单及用户；结果/审核时间索引 | 每次提交复制当时资料，业务字段不再改写；退回后重提增加版本号。审核结果及时间附于该版本，历史可追溯。 |

**业务与查询约定：**备案状态为 `DRAFT → PENDING → APPROVED` 或 `PENDING → RETURNED → PENDING`；只有当前 `APPROVED` 的企业具有后续填报资格。省级列表与导出在 SQL 查询中限定省级组织下的市级组织以及地区树范围；地区筛选包含子地区。调查期只用于已通过列表/导出，条件是当前批准版本的审核时间早于所选期次的 `end_exclusive_at`，不要求晚于期初。通过审核后同步 `org_unit.name` 为批准版本的企业名称，列表和导出仍以提交快照为准。Excel 文件不在数据库存储。

**验证与清理：**第二周 HTTP 集成测试在 H2 与本机 MySQL 8.0.41 临时空库均通过。部署前已备份服务器原数据库和第一周 JAR；2026-10-24 新 JAR 启动后，Flyway 在服务器执行 V3 成功。从本机经服务器公网地址完成第二周全部 14 个操作的真实 HTTP 调用，并检查建号、登录、草稿、字段校验、提交、退回、重提、通过、越权拒绝、地区/期次筛选、13 列 Excel 及空表头文件。测试使用匿名数据；测试账号、备案版本、审核、审计和临时期次已删除。清理后服务器保留 3 个原演示用户、3 个原组织、1 个 `DEMO_2026_10` 期次，备案、版本、审核和审计表均为 0 行。ID 分配器已取过号，保留正常递增值。
